## 1. 原始模型错误回归

同一服务配置下，旧的 `with_structured_output(..., method="function_calling")` 调用实际返回 `BadRequestError`，匹配 `Thinking mode does not support this tool_choice`。

新实现不强制工具选择，使用 JSON object 输出、Pydantic 严格 schema 校验；仅在 JSON/字段不合法时最多修复一次，不通过关闭 thinking 掩盖兼容性问题。真实 Decision、Evidence 调用通过。

实际图路径：

| 输入 | 观察到的路径 | 耗时 |
|---|---|---:|
| 问候 | context → decide → answer → validate | 1.82 s |
| 合成年假资料问答 | context → decide → retrieve → evidence → answer → validate | 3.06 s |

年假回答包含“15 天”及 `[S1]`。该检查是路径、答案关键字与引用格式的冒烟验收，不是语义蕴含评测；补检索/拒答的总体正确率尚未测量。JSON mode 也不等于兼容所有供应商，服务仍须支持 `response_format={"type":"json_object"}`。

### 保留的失败记录

`results/ambiguous-probe-failure.json` 保留了一次退出码为 1 的结果：用例问“假期几天”，证据只给出“年假十五天”，模型认为假期类型不明确，返回 `sufficient=false`。JSON/schema 调用成功，但原用例错误地强制预期 true。

修正为问题与证据均明确“星河公司正式员工每年带薪年假”后重新验证，**仍保留 sufficient=true 的断言**，没有去掉断言来让结果变绿。新记录同时保存完整合成探针和 harness SHA256。另修正了重复 `docker compose cp` 可能套一层同名目录的问题，复跑前核对容器/本机脚本哈希一致。

## 2. 检索评测

两组使用相同语料、问题和 embedding 模型。基线直接取向量 top-3；当前方案召回最多 20 个片段，cross-encoder 重排后取 3 个。评测单位为**top-3 片段内去重后的文档 ID**，不是保证返回三个不同文档。

| 指标 | 向量基线 | 向量召回 + 重排 |
|---|---:|---:|
| 文档 Recall@3 | 1.000 | 1.000 |
| MRR@3 | 1.000 | 1.000 |
| Hit@1 | 1.000 | 1.000 |
| 单查询中位耗时 | 4.74 ms | 662.04 ms |

- Recall：命中相关文档数 / 标注相关文档数，再对问题平均。
- MRR：首个相关文档排名的倒数，再平均；未命中为 0。
- Hit@1：首条结果相关的问题占比。
- 耗时包含 query embedding、数据库检索及该组重排，不包含 LLM 生成、浏览器或完整 HTTP 链路。顺序执行、小样本、本地缓存会影响结果，不能据此宣称线上 SLA。
- 首条重排为 3549.1 ms，包含重排模型加载；入库总耗时 0.48 s。
- **本语料上没有测得重排准确率收益，反而有明显延迟成本**。短语料太简单，两组均触顶，不能用 100% 宣称真实项目达到 100% 正确率。
- 两条无答案探针仍返回 top-k 候选，说明检索器本身不是拒答分类器；此项仅记录，不计算拒答准确率。

## 3. 故障恢复与资料一致性

| 检查 | 注入 / 操作 | 实际观察 |
|---|---|---|
| 重复投递 | 同一 run 8 路并发执行 | 仅 1 条助手消息 |
| 过期租约 | 将心跳回拨后接管 | 旧 owner 提交失败，新 owner 成功 |
| 初次投递丢失 | DB 提交后 Redis lpush 抛错 | 请求 ID 仍返回，reaper 恢复并完成 |
| 完成通知丢失 | SSE 已订阅，但不发布 done | 1.804 s 后通过数据库找回最终结果 |
| Redis 订阅失败 | subscribe 抛连接异常 | SSE 回退数据库终态读取 |
| 模型调用超时 | 替代 Agent 抛 TimeoutError | 安全错误持久化、历史可见、FIFO 后续请求推进 |
| 提交中断 | 最终事务中途注入异常 | 状态/消息回滚，重试后只写 1 条回复 |
| 项目隔离 | 从另一项目检索相同问题 | 无跨项目命中 |
| 修改资料 | 更新正文后用旧 revision 再提交 | 旧片段消失，新片段可检索，旧版本写入被拒绝 |
| 删除资料 | 删除隔离文档后检索 | 文档片段同步清除 |

另 3 项为真实模型/图检查，2 项为真实库快照一致与临时库清理，共 15 项。

### 保证与不保证

- 每次执行使用唯一 lease owner；最终消息、请求/run 终态及同组下一项调度在同一数据库事务中提交。过期执行者不能覆盖新执行者的结果。
- PostgreSQL 是最终结果依据，Redis 负责尽力投递。SSE 定时校验数据库，不仅依赖 pubsub 通知；正文只在事务提交后展示，过程节点仍实时可见。
- **外部模型调用是至少一次，不是 exactly-once**。接管可能再次消耗模型调用；本次证明的是这些场景下的受租约约束、原子化结果持久化。
- 过期租约用“回拨心跳”模拟，不是实际 kill -9 / 断电；Redis 故障通过异常/省略通知注入，不是完整网络分区。未覆盖长期断网、持续数据库故障、并发删除、生产高负载或所有进程崩溃时序。
- 模型错误终结本轮，并允许用户重新提问；不承诺无限自动重试。租约重投也尚无生产级的重试次数上限与告警体系。
