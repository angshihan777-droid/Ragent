编排流程

一条请求，从点击到落库的全链路

Agent 项目的核心是编排。下面这张幕布式流程图展示从前端提问，到 FIFO 组级串行入队、worker 抢租约执行 LangGraph，再到 崩溃时 reaper 自动恢复重投 的完整链路。

① 前端提问 → APIPOST /threads/{id}/messages：写入 user 消息 + 建 agent_run_request(status=queued)
② 组级 FIFO 入队（真相源=Postgres）try_dispatch_group：pg_advisory_xact_lock(hash(user:agent:thread)) 组级事务锁同组同一时刻只放行一个 run
组内已有 dispatched
排队等待新请求保持 queued，不抢占，严格先进先出
组内空闲
取队头建 run → 事务提交后 LPUSHagent_run(status=pending)；commit 后才投递 Redis 队列 ragent:runs，避免脏投递
③ worker BRPOP 领取owner = WORKER_ID:uuid（每次 attempt 唯一）；claim_run 抢租约 pending→running
④ 心跳续约 loop（每 2s）_heartbeat_loop 刷新 heartbeat_at 并校验 lease_owner；租约被别人接管则本 attempt 主动退出
⑤ 执行 LangGraphcontext → decide →(direct/clarify/retrieve)→ evidence →(rewrite 回环≤2 | answer)→ validate决策 + 两阶段检索都在这一步
⑥ finalize_run（单事务）写 result + 终态 done，fenced 防重复插 assistant，并原子派发同组下一个 FIFO
⑦ 崩溃自动恢复（reaper 每 5s）recover_once 扫描 heartbeat_at 超过 lease 超时(10s) 的 running：租约过期 → 打回 pending 重新投递，交给新 owner 重试；Redis 掉线也能靠 PG 对账重建worker 崩溃 / 断网 / OOM 都不丢任务
API Postgres（真相源） Redis（投递通道） Worker 故障恢复
两大亮点

不是"检索器"，而是"会判断的 Agent"

这两点是本项目区别于普通 RAG demo 的关键。

亮点一 · 自主决策检索

先想"要不要查"，再决定怎么答

LangGraph 的 decide 节点让 Agent 自己判断问题类型，而不是无脑检索每一句话：

direct寒暄 / 常识：直接回答，不浪费一次检索
clarify问题太模糊：反问澄清，避免答非所问
retrieve知识型问题：进入两阶段检索，evidence 不足时最多改写回环 2 轮
亮点二 · 两阶段检索 + 重排

pgvector 粗召回，cross-encoder 精排

先用 bge-small-zh-v1.5（512 维）在 pgvector 召回 20 条，再用 cross-encoder 重排取 Top3，答案强制带引用并做校验。

77.9→78.5Recall@10
0.761→0.781MRR
0.714→0.727nDCG@10

评测集 T2Reranking · 切块 384 token / overlap 48。重排显著提升排序质量。
