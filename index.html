编排流程

从点击到落库的完整链路

三元组 FIFO 串行入队、worker 抢租约执行、崩溃后 reaper 自动恢复重投——Postgres 是真相源，Redis 只是投递通道。

  • 01前端提问 → API
    POST /threads/{id}/messages：写入 user 消息，建 agent_run_request(status=queued)
    • 02组级 FIFO 入队Postgres
      try_dispatch_group：pg_advisory_xact_lock(hash(user:agent:thread)) 组级事务锁，同组同一时刻只放行一个 run
      • 组内已有 dispatched → 排队等待
        新请求保持 queued，不抢占，严格先进先出
      • 组内空闲 → 取队头建 runRedis
        agent_run(pending)；事务 commit 后才 LPUSH ragent:runs，避免脏投递
    • 03worker BRPOP 领取Worker
      owner = WORKER_ID:uuid（每次 attempt 唯一）；claim_run 抢租约 pending→running
      • 04心跳续约 loop（每 2s）
        刷新 heartbeat_at 并校验 lease_owner；租约被接管则本 attempt 主动退出
      • 05执行 LangGraph决策+检索
        context → decide →(direct/clarify/retrieve)→ evidence →(rewrite≤2 | answer)→ validate
      • 06finalize_run（单事务）Postgres
        写 result + 终态 done，fenced 防重复插入，并原子派发同组下一个 FIFO
    • 07崩溃自动恢复（reaper 每 5s）故障恢复
      recover_once 扫描 heartbeat_at 超过 lease 超时(10s) 的 running：租约过期 → 打回 pending 重新投递，交给新 owner 重试。worker 崩溃 / 断网 / OOM 都不丢任务
两大亮点

不是"检索器"，而是"会判断的 Agent"

这两点是本项目区别于普通 RAG demo 的关键。

亮点一 · 自主决策检索

先想"要不要查"，再决定怎么答

LangGraph 的 decide 节点让 Agent 自己判断问题类型，而不是无脑检索每一句话：

direct寒暄 / 常识：直接回答，不浪费一次检索
clarify问题太模糊：反问澄清，避免答非所问
retrieve知识型问题：进入两阶段检索，证据不足时最多改写回环 2 轮
亮点二 · 两阶段检索 + 重排

pgvector 粗召回，cross-encoder 精排

先用 bge-small-zh-v1.5（512 维）在 pgvector 召回 20 条，再用 bge-reranker-base 重排取 Top3，答案强制带引用并做校验。切块 384 token / overlap 48。

下表是在 THUIR/T2Ranking dev（50 query · 2000 passages · 5772 chunks）上的真实评测：

检索配置Recall@3MRR@3nDCG@3Hit@1p50 延迟p95 延迟
向量 Top-30.77060.97670.95060.960029.4 ms36.5 ms
召回 20 + 重排 30.77730.98000.96120.98002374 ms3326 ms
召回 100 + 重排 30.75730.96000.93780.940013028 ms17315 ms

召回 20 + 重排 3 是最优点：MRR / nDCG / Hit@1 全部最高。召回加深到 100 反而下降且延迟激增——更深召回并不等于更好。
